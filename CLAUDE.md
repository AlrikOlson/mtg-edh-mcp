# mtg-edh-mcp

## Project prime directive

Read [docs/ENGINE-CHARTER.md](docs/ENGINE-CHARTER.md) before planning or changing this project. The prime directive is full-game simulation for any Commander-legal deck through MCP and the single canonical Rust engine. The fixture and Muldrotha milestones do not complete it. Maintain the native roadmap autonomously as evidence changes: add, split, merge, reorder and correct work within this directive; keep all planned unfinished work and discoveries pending, never in backlog. Before and after every substantial unit, record architecture, ownership, reuse, migration and independent acceptance evidence. Preserve native history, active work and user changes. This is project policy, not a `/goal` task; respect each invocation's implementation bounds.

## Workflow — Plan, Execute, Verify

The project skills and their runtime contract own the exact lifecycle for the requested work. Use native Magistr reasoning, roadmap and execution state, Workbench grounding and verified edits, applicable recorded quality gates and an atomic scoped commit. Follow the matching skill's completion order; do not duplicate or reinterpret its lifecycle here.

Apply the charter's autonomous roadmap maintenance before planning and before closing substantial work. Keep architecture and reuse review active, preserve acceptance and history, and ensure new planned work is pending with dependencies and priority. Planning authority does not start implementation or an unbounded loop. Native roadmap state is authoritative; export a view only when project policy requests it.

# think-and-ship

The four tool families below are served **in-process by the `magistr` MCP server** (`magistr mcp-serve`) over one think-and-ship store. Do not also configure a standalone `think-and-ship serve` on this project: two processes over one store each hold their own copy of the execution and roadmap state (persistence is merge-on-save, never reload-on-read), so a write through one is invisible to the other's guards until restart. `magistr init` retires such an entry.

## Tool families

| Family        | Purpose                                                                 | Key tools                                                                                           |
| ------------- | ----------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| **think_***   | Reasoning trace: record steps, branch hypotheses, pin conclusions       | `think_record_step`, `think_pin_step`, `think_trace_checkpoint`                                     |
| **ship_***    | Execution trace: objectives, tasks, actions, quality gates              | `ship_set_objective`, `ship_plan`, `ship_start`, `ship_record`, `ship_check`, `ship_finalize`       |
| **roadmap_*** | The long-horizon plan-of-plans driving both                             | `roadmap_status`, `roadmap_next`, `roadmap_start_chunk`, `roadmap_complete_chunk`, `roadmap_export` |
| **signal_***  | Stakeholder signals: capture, research, surface, promote to the roadmap | `signal_capture`, `signal_pending`, `signal_research`, `signal_promote`                             |

## Cross-referencing

Link reasoning to execution:

- On `think_record_step`, pass `execution_ref: "task:<id>"` to point at a ship_* task.
- On `ship_record`, pass `think_step: <N>` to point back at the motivating think_* step.

Both halves resolve the same project identity from the working directory so
traces auto-correlate.

## Quick-start workflow

1. `ship_set_objective` — define the goal
2. `ship_plan` — break into tasks
3. `think_record_step` — record your reasoning (open)
4. `ship_start` → `ship_record` → `ship_complete` — do the work
5. `ship_check` — record test/lint results
6. `ship_finalize` — finalize the objective
7. `think_record_step` — record outcome (close)
