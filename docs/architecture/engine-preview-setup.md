# Deterministic canonical fixture setup

This receipt follows the [engine charter](../ENGINE-CHARTER.md) and the [canonical source procedure](engine-source.md). Native chunk `engine-mvp-preview-setup` and think:340 record scope. The [source pin](../../engine/source.json) identifies the complete canonical implementation.

## Ownership and reuse

The canonical Rust `mtg-engine` core gains two seams and no second rules path. `identity::IdentityAllocator` is the single owner of every identity the engine creates while playing: player, physical card and stack object identities come from one reserved `ChaCha` stream derived from the game RNG key, checkpointed as a `GameState` field, so allocation never reads OS entropy and never advances the gameplay stream. Zone incarnations keep the existing reserved `ZoneManager` stream from `engine-mvp-state`. `setup::build_game` is the single physical-setup owner: it allocates seats and copies before the state exists, builds each copy from one shared `CardDefinition` per Oracle identity through the existing factory, inserts through a checked zone path that rejects a duplicated physical identity, orders libraries top-first and advances to the fixture's starting step. `setup::prepare_preview_game` is the strict adapter for the immutable internal fixture: it binds fixture ID, version, complete digest, official rules digest and ordered seat indices before any allocation and qualifies every source through the new `support::qualified_definition`, which `build_qualified_card` now composes.

Shared consumers migrated instead of receiving a fixture-only allocator. `GameState::stack_mut()` returns a `StackMut` facade whose consuming push, pop, resolve, remove and peek verbs allocate from the allocator; every existing gameplay push in casting, activated and loyalty abilities, resolution continuation, ability choices and the loop compiles unchanged and now allocates canonically. `GameStack::push`, `StackObject::new` and their effect variants take an explicit `ObjectId`; `Player::with_identity`, `CardBuilder::id` and `build_card_from_definition_with_id` accept allocated identities. The fixture conformance suite obtains its state from the canonical setup owner instead of a test-local builder. Entropy-backed `new()` constructors remain for authoring clients and tests that never checkpoint or compare states; no production path creates tokens or copies yet, and future runtime creation must allocate through the same owner.

MCP remains the catalog and construction authority; `capturePreviewFixture()` and `validateDeck` are untouched. The worker protocol 4 contract, generated bindings and fixture artifact bytes are unchanged; only the source pin and contract manifest revision advance. No TypeScript gameplay, fallback, public MCP route or worker execution capability was added.

## Boundaries and honest limits

`PreparedGame` returns the state, ordered seats and a physical inventory keeping Oracle identity, printing identity and physical `CardId` distinct with each card's owner, starting zone and position; supplied color identity and face data flow through the existing definition without a GUI, starter-deck parser or runtime lookup. `CORE_SNAPSHOT_VERSION` is 5 because the allocator cursor is part of the exact core envelope; version 4 snapshots reject explicitly.

`build_game` refuses any seat count other than two with a typed error until `engine-mvp-multiplayer`; four-seat Commander setup, command zones, mulligans, tax/history and the 400-card benchmark stay with `engine-mvp-multiplayer`, `engine-mvp-commander` and `engine-mvp-catalog-objects`. Seeded fixture repetition and exact core restore prove identity continuation of the core only; live scheduler, priority, pending decision and policy continuation remain `engine-mvp-runtime-checkpoint`. Admission, a bounded run and real MCP play remain `engine-mvp-preview-worker` and `engine-mvp-preview-mcp`. Legacy TypeScript gameplay stays frozen until `engine-mvp-cutover`.
