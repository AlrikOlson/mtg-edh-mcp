# Print job store: durable print orders and the user's print preset

Accepted for `print-job-store` under the [engine charter](../ENGINE-CHARTER.md). It is the second unit of the Proxy Order Helper (the `print_*` tools) planned by the roadmap refresh `think:440`; the plan and grounding are `think:444` and the closing finding is recorded on the chunk. Native Magistr records hold execution status.

## What was delivered

`src/print/jobStore.ts` exports `PrintJobStore`, served by `UserDataStore.print`. The user-data store moves to schema version 2.

| Concern            | Behaviour                                                                                                                                                                                                                                                                                                                                                       |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Schema version 2   | `print_jobs` (indexed `job_id`, `principal`, `deck_id`, `deck_version`, `status`, timestamps, JSON `payload`) and `print_presets` (`principal`, JSON `payload`). A partial `UNIQUE` index over `(principal, deck_id, deck_version) WHERE status IN (prepared, reviewed, starting, filling)` makes "one open job per reviewed deck version" a database invariant |
| Migration          | A version-1 database validates, then migrates once on open inside the driver's `BEGIN IMMEDIATE` transaction, so the existing pre-operation backup is written before the DDL. The migration runs under the startup gate, so two processes cannot both migrate. A version-1 backup still restores and migrates again on the next open; a newer schema is refused |
| Startup validation | At version 2, `validateUserDataDatabase` parses every stored job and preset the way it already parses decks and collections, so `doctor`, `restore-user-data` and open refuse a corrupt print row instead of guessing                                                                                                                                           |
| Job record         | `record_version`, `job_id`, `principal`, `status`, timestamps, the pin (`deck_id`, `deck_name`, `deck_version`, `data_snapshot`), the reviewed `manifest` exactly as built, `images` per slot (`front`/`back` as a catalog printing by Scryfall id or a user file), `settings` (stock, foil, card back), `job_dir`, `project_name`, `progress`, `failure`       |
| Create and reuse   | `create` seeds settings and per-slot images from the principal's preset, lets explicit prepare-time choices win, and returns the principal's open job for the same deck id and version (`created: false`) with its directory and project name intact instead of writing a duplicate                                                                             |
| Isolation          | `get`, `findOpen`, `list`, `update` and `transition` are principal-scoped; another principal's job id reads as `null` or `not_found`                                                                                                                                                                                                                            |
| Status machine     | prepared -> reviewed -> starting -> filling -> filled; `failed` and `cancelled` from any live step; `failed -> starting` retries in place so the filler resumes the same printer project; `filled` and `cancelled` are final. Images and settings change only while prepared or reviewed, and a change returns a reviewed job to prepared                       |
| Drift              | `deckDrift(job, liveDeck)` reports `current`, `moved_on` (with the live version) or `deleted`; the stored job never changes when the deck does                                                                                                                                                                                                                  |
| Preset             | `getPreset` and `setPreset` keep preferred printings per oracle id (a `null` forgets one), the card back, stock and foil; the default is Standard Smooth, no foil, printer card back                                                                                                                                                                            |

Job directories are `<data root>/print-jobs/<job_id>`; the printer project name is `mtg-edh-print-<first eight characters of the job id>`. Both are stored on the record and never recomputed. The store records the directory; the project-file owner creates and writes into it.

## Ownership and reuse review

- **One owner for the order.** The job store is the only place a reviewed order, its artwork choices and its status live. The image selector (`print-image-selector`) reads `images` and the manifest's faces; the project file (`print-project-file`) reads slots, settings and `job_dir`; the filler (`print-mpc-filler`) reads `project_name` and reports `progress` and `failure` through `transition`; the MCP tools (`print-mcp-tools`) call `create`, `update`, `transition` and `deckDrift`.
- **Inside user data, not a third SQLite file.** Engine jobs live in `engine-jobs.sqlite` because they are derived evidence. Print choices are authored user state: artwork preferences and reviewed orders must survive and restore together with the decks they print, so they share `user-data.sqlite`, its transaction, its pre-operation backups and `restore-user-data`. The chunk record asked for exactly this migration.
- **Reused.** `SqliteUserDataDriver.transaction` and `beforeWrite` (backup discipline), the `StructuredError("STORAGE_ERROR")` convention, the engine job store's principal-scoped read and JSON-payload-row pattern, and the manifest owner's `PrintManifest`. The manifest schema in the job store is checked against the manifest type with `satisfies`, so the two cannot drift silently.
- **Added seam.** `PrintDataDriver` in `src/storage/driver.ts` is separate from `UserDataDriver`, so the deck and collection stores and their recording test drivers are untouched.
- **Overlap.** None added. No engine, catalog, deck-store or validator change. `setup.ts` diagnostics keep calling the same validator and accept both schema versions.
- **Left for their owners.** Choosing a default printing and fetching images (`print-image-selector`); creating the job directory and writing the project document (`print-project-file`); the filler and its resume (`print-mpc-filler`); MCP exposure and the drift notice wording (`print-mcp-tools`).

## Migration note for operators

A version-1 `user-data.sqlite` is upgraded on the first open by this release; the pre-migration image is the newest file in `backups/`. An older release refuses a version-2 database with the existing "unsupported or incomplete user-data schema" message; to go back, stop the servers and run `restore-user-data` with that pre-migration backup.

## Evidence

Scenarios were written first and failed on the missing module and the refused version-1 fixture. `src/storage/userData.test.ts`: a programmatic version-1 fixture (two principals' decks, a snapshot, a collection) opens, keeps everything, lands at version 2 after exactly one backup whose own version is 1, and does not migrate again on reopen; a version-1 backup restores and migrates on the next open; a new database is created at version 2 with the five tables; a version-3 database is refused. `src/print/jobStore.test.ts`: a job is pinned, stored with its directory and project name and read back after reopening; the open job is reused for the same deck version and a new one starts after cancellation; jobs are hidden across principals; the stored job is unchanged after a deck mutation while `deckDrift` reports current, moved on and deleted; the preset persists across reopen, seeds the next job, is overridden by explicit choices and merges per key; the status machine rejects skipped steps, resets to prepared on edits, locks while filling, retries a failed job in place and freezes a filled job; writes roll back on an injected commit failure, take a backup, and share one transaction and one backup with a deck write; a database holding a malformed job is refused at open.

Recorded gates: TypeScript typecheck; vitest for the print, storage, setup, storage-process, refresh and deck-store test files (every `UserDataStore` consumer); ESLint and Prettier.
