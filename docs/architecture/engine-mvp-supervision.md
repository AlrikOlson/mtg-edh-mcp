# Supervising engine jobs: memory ceiling, durable principal-scoped jobs, explicit cancel

This receipt follows the [engine charter](../ENGINE-CHARTER.md), the [preview MCP receipt](engine-preview-mcp.md) and the [headless worker receipt](engine-mvp-worker.md). Native chunk `engine-mvp-supervision` and think:428–430 record scope. The engine [source pin](../../engine/source.json) is unchanged at `34e82c7` (protocol 6); no canonical Rust source or contract byte changed in this unit. The delivered scope is narrower than the chunk's original acceptance: the Tasks extension is split into its own pending chunk (below), because the installed SDK has no runtime for it.

## Ownership and reuse

The canonical Rust core stays the sole owner of every game decision; the `mtg-worker` process stays the only executor. Nothing here builds a card, a state or a rule. The unit extends the two existing TypeScript process owners and adds two owners beside them.

| Concern                                                                                                  | Owner                                         | What changed                                                                                                                                                                                                                                                             |
| -------------------------------------------------------------------------------------------------------- | --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Child-process supervision (argv, framing, drained pipes, deadline, byte ceilings, cancel, kill, receipt) | `src/engine/supervisor.ts` (existing)         | Gains the parent-enforced memory ceiling: `RunOptions.maxMemoryBytes`, a `MemoryProbe` seam with the platform default, termination `memory_limit`, and `peak_rss_bytes` plus `memory_enforcement` in the receipt.                                                        |
| One bounded fixture run per request (handshake, admission, trial seed, progress trace, relay)            | `src/engine/previewRun.ts` (existing)         | Passes its declared 256 MiB ceiling to the supervisor; the receipt now names the enforcement method instead of `none`. Nothing else changed.                                                                                                                             |
| Durable job records                                                                                      | `src/engine/jobStore.ts` (new)                | `engine-jobs.sqlite` in the data root: WAL, `synchronous = FULL`, one `BEGIN IMMEDIATE` transaction per write, `UNIQUE (principal, idempotency_key)`, strict zod envelope, foreign schema versions refused.                                                              |
| Queueing, concurrency beyond the busy refusal, cancellation, recovery, principal scoping                 | `src/engine/jobs.ts` (new `EngineJobService`) | Wraps the preview service; owns no worker and no game state.                                                                                                                                                                                                             |
| MCP route                                                                                                | `src/server/engineTools.ts` (existing file)   | `engine_job_submit`, `engine_job_status`, `engine_job_cancel` registered beside `engine_preview_fixture`, scoped by the server's `session`; `createServer` gains `engineJobs`; `main` opens the store when the preview is enabled and stops running jobs before exiting. |

Why a separate database rather than a table in `user-data.sqlite`: the user-data store is schema-versioned with backups and restore, and refuses any other `user_version`, so a jobs table there would force a migration of every install for state that is not user-authored. Jobs are derived engine evidence. Keeping them in their own file also makes the acceptance item "simulation cannot mutate authored decks" structural: the job service holds no deck store, and the transport scenario proves a deck created through `deck_create` is byte-identical across a job.

Why the memory ceiling is a poll: Node exposes no API for another process's resident size, and a hard OS limit would have to be set inside the worker (the parent has no `setrlimit` on a child). The supervisor therefore samples every 250 ms while a ceiling is declared, through `/proc/<pid>/status` (`VmRSS`) where procfs exists and otherwise `ps -o rss= -p <pid>` with a fixed argument array and no shell, and reports the method in the receipt (`proc_status`, `ps_rss`, `unavailable` when the probe failed, `none` when no ceiling was declared). A probe failure stops sampling and never ends the run; the elapsed deadline and byte ceilings still bound the worker.

Duplicate paths: none created. The job service does not re-implement the run; it calls `PreviewFixtureService.run` with its own abort signal and progress hook, so admission, seeds, the relay and the receipt have one owner. The request-scoped preview tool and the job route share one supervisor and one concurrency ceiling; a job refused as `busy` by that shared runner returns to the head of the queue and retries. At `engine-mvp-cutover` the job service serves the public simulation owner with an authored-deck admission in place of the fixture; nothing here is a fallback or a second executor.

## Job semantics

- Submission validates the preview tool's own bounded shape plus an optional `idempotency_key`; the relay client stays refused (a job has no decision client). The record (immutable inputs with the derived trial seed, fixture digest, engine and protocol versions, the served data snapshot) is committed before the handle is returned; a storage failure refuses the submission and starts no worker.
- Same principal and key: one job, whether the repeat arrives concurrently, after completion, or from a later process (live, recent and stored records are consulted in that order). The same key under another principal is another job.
- Queue: FIFO behind `maxRunning` (1 by default, the runner's own ceiling), with `maxQueued` (16) and `maxQueuedPerPrincipal` (4) refusals as `ENGINE_JOB_QUEUE_FULL`. Running jobs do not count against the queue.
- Terminal state: the worker's own outcome (`completed`, `truncated`, `cancelled`, `unsupported`, `invalid`, `engine_error`) with the report exactly as the preview tool presents it, or `failed` with the `PreviewRunError` code, reason, message and the supervisor receipt. A requested cancel that the supervisor had to enforce (hard kill) is `cancelled` with the receipt showing `hard_killed`.
- Cancellation is explicit. A waiting job is terminal at once without a worker; a running job is acknowledged (`cancel_requested_at`) and becomes terminal only when the worker reports `cancelled` or the supervisor has terminated it. Closing the submitting connection, closing an HTTP response stream, or a `notifications/cancelled` for the submit request never cancels a job. The tool result distinguishes `cancelled_before_start`, `acknowledged` and `already_terminal`.
- Progress: the last progress event and the event count are kept on the live record (in memory; persisted with the next state change), so a status poll shows a run advancing.
- Recovery: on construction the service marks every stored `queued` or `running` record `failed` with `interrupted/process_restart`; there is no worker and no checkpoint to resume from (`engine-mvp-runtime-checkpoint`).
- Shutdown: `main` stops accepting jobs, cancels waiting ones, aborts running ones and waits (bounded by the kill grace, 10 s fallback) before exiting on stdin end, so no worker outlives the server.
- A failed persist of a state change is logged and recorded as `persistence_error` on the in-memory record, which stays authoritative and visible; the store keeps the last state it could commit.

## SDK and the Tasks extension

The installed `@modelcontextprotocol/server` 2.0.0 (with `core` and `client` 2.0.0) carries the 2025-11-25 Tasks wire vocabulary (`tasks/get`, `tasks/result`, `tasks/list`, `tasks/cancel`, `TaskStatus`, `CreateTaskResult`) explicitly marked `@deprecated 2025-11-25 wire vocabulary with no SDK runtime; kept importable for interoperability only`, and `ToolExecution.taskSupport` exists only as a schema field. The 2026-07-28 changelog moved tasks out of the core protocol into the draft extension `io.modelcontextprotocol/tasks` (polling `tasks/get`, `tasks/update` for input, `tasks/cancel`; `tasks/result` and `tasks/list` removed; statuses `working`, `input_required`, `completed`, `failed`, `cancelled`; `pollIntervalMs`, `ttlMs`). The installed SDK can serve neither, so this unit delivers the bounded explicit workflow the chunk requires for hosts without Tasks, and the extension moves to the new pending chunk `engine-mvp-tasks-extension` (a dependency of `engine-mvp-mcp-workflow`), to be built as an adapter over `EngineJobService` once an SDK runtime or a hand-rolled extension handler is chosen there. The registry's request-id cancellation shim is unchanged and still retires under `engine-mvp-sdk-cancel-shim-retire`.

The pre-existing hang, crash, malformed, flood, abort-race, busy and spawn-failure scenarios are unchanged.

- `src/engine/jobs.test.ts` (13, real fake-worker processes and a real temporary store): durable creation before the handle with the worker's own outcome and receipt; five concurrent submissions with one key are one job and one worker, and the key still names the job after completion and across principals; invalid input never spawns; an injected commit failure refuses with `STORAGE_ERROR` and the retry creates the job; FIFO order, per-principal and global caps, cancel of a waiting job without a worker, acknowledged cancel of a running job ending in the worker's `cancelled` outcome, a second cancel `already_terminal`; a worker that ignores the cancel is hard-killed and the job is `cancelled` with the receipt; a crash is `failed/crashed`; `unsupported` and `engine_error` outcomes stay the job status; a job waits for the shared runner while a request-scoped preview holds its slot and runs afterwards; stored `running` and `queued` rows are marked interrupted at construction; a failed terminal persist stays visible with `persistence_error`; shutdown cancels waiting jobs, aborts running ones and leaves no live worker.
- `src/server/engineTools.test.ts` (23 scenarios, 5 native): the job tools exist only with an injected service; over real stateless Streamable HTTP a job submitted by one connection keeps running after that client closes, `ping` from another principal answers within two seconds, the other principal receives `ENGINE_JOB_NOT_FOUND` on status and cancel, the owner's cancel is acknowledged and the terminal state is the worker's own cancelled outcome with a closed receipt; a legacy 2024-11-05 client submits, repeats the key, polls to `completed` and reads the stamped snapshot; undeclared and inconsistent inputs are refused before any worker and a crash is a failed job with its receipt; a deck is byte-identical across a job; over a real stdio server process a raw `notifications/cancelled` for the submit request (JSON-RPC id 0) leaves the job running, and closing stdin makes the server cancel the job cooperatively and persist it before exiting; against the pinned native worker a submitted job reaches the turn-five victory with four events and a clean receipt.

## Limits

Only the immutable two-to-four-seat internal fixture runs as a job; there is no authored-deck, Commander or Muldrotha claim. The memory ceiling is a 250 ms poll, so a burst above the ceiling shorter than one interval is not caught, and on Windows neither probe exists (`unavailable`). The job store is per data root and per process: two servers over one root would each recover the other's live jobs as interrupted, which is a limit of the single-process local deployment, not a supported topology. Terminal records stay in the store indefinitely (no retention policy). Cancellation observed by the submitting client is always through `engine_job_cancel`; the Tasks extension, `tasks/update` input and any host-negotiated task cancellation belong to `engine-mvp-tasks-extension`. Nothing was pushed or published; no roadmap file was exported.
