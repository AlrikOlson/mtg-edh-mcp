Accepted for `print-mcp-tools` under the [engine charter](../ENGINE-CHARTER.md). ## The flow on the wire

1. `print_prepare {deck_id}` -> `job_id`, `status: prepared`, `cards[]` (slot, name, source, front and back refs, `front_ready`, `back_ready`), `card_back`, `settings`, `tokens[]` (information only), `attention[]`, `complete`. The same deck version returns the open job with `created: false`.
2. `print_update {job_id, images, card_back, stock, foil, remember}` -> the same view after a new resolution. Faces set to `null` are cleared; a slot set to `null` clears both faces. A job past `reviewed` is `PRINT_JOB_LOCKED`.
3. `print_start {job_id}` -> `status: starting` and the project name; the fill continues after the call. Refused with the attention list while faces lack images, with the filler's attention item (`worker_missing`, `browser_missing` and its install command, `worker_failed`) while it cannot run, and `busy` while an earlier browser is still held. The job is left `reviewed` with its project written in the unavailable case, so the next start skips straight to the fill.
4. `print_status {job_id}` -> the job view plus `drift` (`current`, `moved_on`, `deleted` with the pinned and live versions), `notices[]`, `progress`, `failure`, `fill` (`ssid`, `review_url`, `instructions`) and `evidence` (`job_dir`, `project`, `cards_xml`, `screenshot`, `fill_state`, each only when the file exists). Job statuses are `prepared`, `reviewed`, `starting`, `filling`, `filled`, `failed` and `cancelled`, as the job store defines them.

The attention item shape is one across the three sources: `kind`, `ref` (oracle id, token id, `card_back` or `filler`), `slots[]`, optional `face`, `name`, `command` and `candidates`, and `message`. Manifest irregularities (`illegal_card`, `commander_in_library`, `missing_faces`, `unknown_token`) are information and never block a start; image items block until resolved; filler items block until the install or rebuild is done.

## `review.json`

The job record persists choices, settings and status, not the outcome of the last image resolution. The service writes `review.json` (`mtg-edh-print-review` version 1: `complete`, per-slot refs and readiness, the card back, the image attention items) into the job directory after every resolution, so `print_status` can show what the user last saw without a network request and after a restart. It is a cache of the selector's answer, never an input to any owner: the next `print_prepare`, `print_update` or `print_start` resolves again and rewrites it.

## Ownership and reuse review

- **No owner was duplicated.** The service calls `buildPrintManifest`, `PrintJobStore.create/update/transition/setPreset`, `resolvePrintImages`, `writePrintProject` and `PrintFillerService.run/probe/shutdown`; it recounts nothing, chooses no image, writes no slot and changes no status except `prepared -> reviewed` through the store.
- **A stored choice is never substituted.** Persisting the selector's `chosen` map wholesale would have erased a mismatched printing and silently chosen the default next time; only `null` faces are filled in, so a `printing_mismatch` keeps pointing at the user's choice until they change it.
- **One instance per process.** Like the engine jobs, the service and its filler are constructed once in `main.ts` and shared by every per-request HTTP server; the catalog tests inject a service over a temporary `UserDataStore` so the description lint covers the new tools.
- **The server never loads Playwright, and sharp only on demand.** The service imports the fill-state filename from `fillProject.ts`, whose only Playwright import is a type; `dist/main.js` still carries no reference to it, and the filler worker remains the only bundle that does. Registering the tools at startup pulled `imagePrep.ts` into the server's import graph, so `imagePrep.ts` now loads `sharp` on first use rather than at module load: a missing native binary still surfaces on a print image step, never as a startup failure, as the umbrella decision requires. The recorded build check greps `dist/main.js` for both properties; the test fixture bundles that compile the server externalise `sharp` next to `better-sqlite3`.
- **Tokens.** The manifest offers token extras and the tools show them, but no downstream owner prints them yet; recorded as pending roadmap work (`print-token-extras`) rather than half-done here.
- **Payment.** No tool, frame or page call proceeds past the printer's preview page; the skill reference says so to the user before a start.

## Known limits

- The live run against the user's MakePlayingCards account remains the manual checkpoint in the umbrella document; `print_start` has been exercised with the fake worker and the recorded fixture site only.
- `fill.instructions`, `fill.ssid` and `fill.review_url` live in process memory; after a restart `print_status` still reports the job's status, failure step and the files, but not those three.
- `print_status` runs the filler probe (a short worker spawn, no browser) whenever the job can still start; a machine without the worker bundle or a browser answers in well under a second.
- Token extras are listed, not printed.
