Accepted for `engine-mvp-worker` under the [engine charter](../ENGINE-CHARTER.md). The chunk was written before the units it depends on existed; by the time it became ready, [bounded fixture execution](engine-preview-worker.md), [Commander play](engine-mvp-commander.md), [catalog objects](engine-mvp-catalog-objects.md), [runtime support enforcement](engine-mvp-support-runtime.md) and the [decision relay](engine-mvp-decision-relay.md) had delivered most of its acceptance through the one worker they share. The research finding and plan are `think:424` and `think:425`; the implementation findings are `think:426`. Native Magistr records hold execution status.

The [source pin](../../engine/source.json) advances to canonical `mtg-game-engine` commit `34e82c78770a11f6ef659f25091f4d046f52d60b` on `main`. The root `Cargo.lock` is byte-identical; the worker contract schema and both generated bindings are unchanged, and only the synced protocol README moves.

## Scope

Against the chunk's four acceptance items, the code at the previous pin already delivered the first two and half of the third: the worker admits immutable catalog captures bound to a fixture scenario (never a CLI starter-deck string), handshakes, preflights strictly and plays the two-seat fixture to a rules outcome through one `prepare_preview_game` and one `GameLoop`; the desktop was moved onto the same setup owner; `tests/native_run.rs` proves framing and bounded progress through the real spawned executable and the MCP supervisor proves hangs, crashes, malformed frames and stderr floods against a scripted worker. Three things were missing, and this unit delivers them:

1. **Crash reporting.** A panic on the run thread never sent `Incoming::Done`, so the session went on waiting for frames and the parent saw only its own deadline, misattributed and after the whole elapsed budget.
2. **stderr and failing-exit evidence through the real executable.** Every native test asserted an empty stderr and a zero exit; nothing exercised the process's own diagnostics.
3. **A dependency-graph guard.** `cargo tree` showed no GUI or network crate, but nothing would have caught one.

The chunk's delivery-order note asked for the Commander scenario to reach the run executor. That integration is not delivered here, on purpose: the pending `engine-mvp-mulligans` record already carries the worker hook (replace `starting_procedure_unavailable` with the canonical shuffle, draw and mulligans, retain the admission with its initial hash, and run it through the existing trial driver with a Commander setup beside the preview setup), and under the Commander profile the canonical qualifier still adds unqualified physical-adapter and shared-rules requirements to every card, so no pod could reach that seam today. Delivering it here would either invent a starting procedure, which the Commander unit refused, or build a second design the mulligans owner would have to undo. The chunk record is rewritten to say so.

## Ownership and reuse review

- **One driver, one executor.** The seam is a function pointer with the driver's signature, not a trait or a second driver: production has exactly one value to pass, and the source guard now checks that value at both call sites. A scenario that injects another executor proves the session, not the engine.
- **A panic is an engine error, not a verdict about the input.** The charter keeps mandatory outcomes, voluntary choices, cancellation, caps and engine failures distinct. A panic is reported under the existing `engine_error` outcome with its own code, never as `unsupported`, a loss, a pass or a cap; the session keeps serving, since nothing outside the panicking thread's stack was touched.
- **The parent still owns termination.** The panic catch removes one silent hang; it does not replace the supervisor's deadline, SIGTERM and SIGKILL, which stay the parent's and are still what ends a genuinely hung worker (`engine-mvp-supervision`).
- **The guard reads the selected graph, not the lock file.** The first draft walked the workspace `Cargo.lock` and failed at once, because the lock records the engine's optional `download` dependencies (reqwest, hyper, tokio, native-tls, openssl, rustls, flate2) whether or not any feature enables them. The selected graph is what a locked build links; the guard was checked to fire on the engine with `download` (ten denied crates), on `mtg-cli` (eight) and on `mtg-desktop` (twenty-three).
- **Overlap.** None added. No contract change, no TypeScript gameplay, no rule.

## Limits

- No panic is reachable through the wire today: the in-process seam proves the session's handling, and the real-executable scenarios prove the transport's own failure paths. The stderr panic line is the standard library's hook, which this unit does not replace.
- A panic on the reader thread or the main thread still ends the process (exit code 101 with the hook's stderr line), which the supervisor reports as `crashed` with that exit code; only the run thread is caught, because only it holds a run the parent is waiting on.
- The dependency guard runs `cargo` from inside the test and therefore proves the graph on the machine that runs the tests; the packaging gate (`engine-mvp-package`) must still inspect the graph of the artifact it ships.
- The Commander run integration remains with `engine-mvp-mulligans`, and admission of a real deck remains closed by the Commander support profile until the corpus units qualify whole cards.
