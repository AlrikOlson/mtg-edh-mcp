# Print project file: the frozen order and its `cards.xml`

Accepted for `print-project-file` under the [engine charter](../ENGINE-CHARTER.md). It is the fourth unit of the [Proxy Order Helper](print-order-helper.md) planned by the roadmap refresh `think:440`; the plan and grounding are `think:448` and the closing finding is recorded on the chunk. Native Magistr records hold execution status.

## What was delivered

`src/print/projectFile.ts` exports `buildPrintProject(job, resolution)`, `renderCardsXml(project, jobDir)`, `writePrintProject(job, resolution)`, the `PrintProjectSchema` (version 1), `MPC_BRACKETS` with `bracketFor(quantity)`, and the two file names. It reads the stored job (`job_dir`, `project_name`, `settings`, the pinned deck identity and the manifest) and the image selector's `PrintImageResolution`, and writes into the job directory.

## Spec correction

The chunk description listed a `<bracket>` element inside `<details>`. The wiki page names bracket only as the ceiling for `quantity`, the frontend exporter (`frontend/src/features/download/downloadXML.ts`) writes `quantity`, `stock` and `foil` only, and the desktop tool reads exactly those three (`order.py`, `Details.from_element`). The bracket therefore lives in our project document, where the filler needs it to pick the site's order size, and the chunk record was updated (`think:448`).

## Ownership and reuse review

- **One owner for the frozen order.** Only `projectFile.ts` turns a resolved job into files; the filler reads `project.json` and never recomputes slots, grouping or the bracket. `cards.xml` is a projection of the same project object, never a second source.
- **Nothing re-decided.** Faces come from the manifest owner, image files and their source references from the image selector, stock, foil, card back, job directory and project name from the job store. The module recounts nothing.
- **Single sources.** `PRINT_STOCKS` stays in `jobStore.ts`; the bracket list lives once here; the template constants stay in `imagePrep.ts`; the print-jobs directory name is `PRINT_JOBS_DIRECTORY` in `userData.ts`, now shared with the doctor. The selector's private atomic writer became the exported `writeFileAtomically` instead of a copy.
- **Schema fidelity over the description.** The export follows the live MPC Autofill schema (no `bracket`, no `query`, `backs` omitted when empty, `cardback` always present) so the manual fallback stays importable by both the desktop tool and the web editor.
- **Left for their owners.** Writing the project at `print_start` and surfacing the retained paths (`print-mcp-tools`); reading `project.json`, uploading each image once per group and the resume logic (`print-mpc-filler`); token extras are not resolved by the selector yet and so never reach the project file.
- **Overlap.** None added. No engine, catalog, deck-store or validator change.
