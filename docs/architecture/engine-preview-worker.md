# Bounded fixture execution in the native worker

This receipt follows the [engine charter](../ENGINE-CHARTER.md) and the [canonical source procedure](engine-source.md). Native chunk `engine-mvp-preview-worker` and think:342 record scope. The [source pin](../../engine/source.json) identifies the complete canonical implementation.

## Ownership and reuse

The canonical Rust `mtg-engine` core stays the sole owner of setup, legality, payments, priority, resolution, combat, terminal evaluation and execution control; this unit adds no rule, no second executor and no core change. The `mtg-worker` package gains three modules over existing owners. `policy` defines the named, versioned decision clients `fixture-baseline@1` (play a land, cast the first legal spell, otherwise pass; every legal attacker attacks; no blocks) and `fixture-pass@1`, both declaring observation version 1: they choose only among the options `enumerate_actions` returns and never mutate state or read hidden zones. `trial` binds an admitted scenario through `setup::prepare_preview_game`, wires the clients into `GameLoop`, charges the declared budgets through `ExecutionControl` and translates the loop's result into one distinct wire outcome. `session` owns one bounded connection: handshake, at most eight idempotent admissions keyed by scenario and catalog digests, one live run on its own thread, out-of-band cancellation and a bounded backlog of requests waiting behind the run. The shared preview binding that `profile_preflight` already performed is now `preview::bind`, reused by admission so there is one binding owner; admission additionally proves setup once and reports the canonical initial hash.

Protocol 5 remains the single versioned private contract at canonical `crates/mtg-worker/protocol/contract.json`; both bindings, the shared fixtures and the README were regenerated and imported through the existing sync. `admit` now carries the scenario, the verified catalog it binds through `snapshot_digest` and the expected qualification implementation, because a bare scenario cannot bind catalog bytes. `Limits` declares `max_work` so the canonical work budget is explicit. `admitted` carries the catalog digest and initial state hash; `completed` carries the rules reason, initial and final core hashes, turns and actions. Capabilities advertise admission, execution and cancellation; `decisions` stays false because no interactive decision channel is delivered.

MCP remains the catalog and construction authority: `capturePreviewFixture()` and `validateDeck` are untouched and no public MCP route, TypeScript gameplay or fallback was added. The TypeScript boundary tests learned the protocol 5 shapes and one real admit-and-run round trip; the worker-owned trial seed derivation is reproduced only inside that test harness.

## Behavior and limits

A run must name a retained admission, its scenario digest, a trial index below the declared trial count and the derived trial seed (SHA-256 over a fixed domain, the scenario seed and the big-endian trial index), so seeds are independent of scheduling. `max_turns` pauses the live scheduler at the turn boundary; `max_actions` and `max_work` are cumulative canonical counters; `max_actions_per_turn` is a per-turn ceiling on the same counter; `max_elapsed_ms` arms a watchdog that raises the canonical cooperative stop token; `max_output_bytes` refuses any progress event that would not leave room for the outcome and raises the same token. The first reason to raise the token wins, so a stop is reported as `cancelled`, `truncated/elapsed_limit` or `truncated/output_limit` and never inferred. `max_memory_bytes`, `concurrency`, hard timeouts and process termination stay with the parent supervisor (`engine-mvp-supervision`).

Input is read on a dedicated thread. A cancel naming the live run raises the stop token at once and is answered after the run's outcome, as `cancelled` when honored or `invalid/cancel_late` when the run had already finished. Every other request waits behind the run in arrival order (at most 64) and is answered afterwards; a clean end of input still answers them. Progress events are acknowledged before the run continues, and frames already delivered are handled before that acknowledgement, which makes output accounting and a cancel delivered before an acknowledgement deterministic.

Honest boundaries: only the immutable two-seat internal fixture admits; a Commander scenario answers `unsupported/commander_admission_unavailable`. The engine's agent interface still passes the whole state to a client, so observation scoping is a discipline of the named clients until the hidden-information owner narrows the interface. The baseline client never blocks and performs no search; `search_nodes` is retained as a declared ceiling. A pending engine choice the worker cannot relay ends the run as `unsupported`. Whole live scheduler serialization, replay and real MCP play remain `engine-mvp-runtime-checkpoint`, `engine-mvp-replay` and `engine-mvp-preview-mcp`.
