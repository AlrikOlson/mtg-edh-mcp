Accepted for `print-mpc-filler` under the [engine charter](../ENGINE-CHARTER.md). It is the fifth unit of the [Proxy Order Helper](print-order-helper.md) planned by the roadmap refresh `think:440`; the research is `think:450`, the plan `think:451`, the implementation findings `think:452` and the closing finding is recorded on the chunk. ## How a fill runs

1. `print_start` (pending, `print-mcp-tools`) calls `PrintFillerService.run`. The service checks the job's status and `project.json`, asks the worker which browsers exist, creates `<data root>/print-browser-profile` (mode 0o700) and moves the job to `starting`.
2. The worker opens the browser on that profile. If the account is signed out it opens `login.aspx` and polls for the sign-out link for up to fifteen minutes; the user signs in by hand and the profile keeps the session. No credential ever reaches the filler.
3. The saved-projects page is searched for a project with the job's name. Found: it is reopened at its `ssid` and the slots the printer already shows filled are skipped. Not found: the product page is filled (stock by its visible text, bracket by value, foil as `EF_055`) and `doPersonalize` opens a new project.
4. Fronts: the mode frame gets the quantity and "different for all fronts"; the slot count must equal the order or the step fails. Each front image is uploaded once (its `pid` is checked against `dn_getImageList`) and placed on each of its slots. The project is saved under the job's name.
5. Backs: two steps on. With per-card backs the mode is "different" and the card back fills every slot without its own back; with only a card back the mode is "same" and it fills the single design; with neither the mode is "same" and the design stays empty, which is the printer's blank default back.
6. Two more steps reach `dn_preview_layout.aspx`. The outcome is `filled` with the `ssid` and the review URL; the job is `filled`; the browser stays open for the user to add the project to the cart and pay. The filler never does.

## Ownership and reuse review

- **One owner for the site.** Selectors, URLs, page JavaScript names and timing live in `mpcSite.ts`; the fake site and the recorded fixture pages implement and exercise the same interface, so drift shows up as a named selector failure in one place.
- **One owner for the order of steps.** `fillProject.ts` reads `project.json` (slots, groups, bracket, stock, foil, card back) and never recounts, regroups or re-decides images; the project file owner stays the authority.
- **One owner for process discipline.** The engine's supervisor was generalised rather than copied: deadline, output ceilings, cooperative cancel, SIGTERM then SIGKILL and the "no orphan" receipt are shared. The frame decoder moved to `framing.ts` so neither wire re-implements it.
- **One owner for status.** Transitions and progress stay in the job store; the service only calls them. `recordProgress` is the one addition, and the status machine is unchanged.
- **Dependency.** `playwright` 1.64.1 is a runtime dependency with no install script, so `npm install` downloads no browser; see the umbrella for the footprint and the on-demand install.
- **Boundary kept.** The MCP server never loads Playwright; a missing browser is an attention item from `probe()`, never a startup failure.
- **Left for their owners.** Registering `print_start` and `print_status` and wiring the service into the server (`print-mcp-tools`); the live run against the user's account (manual checkpoint in the umbrella).
- **Overlap.** None added. No engine rules, catalog, deck-store or validator change.

## Known limits

- The saved-projects list markup (a row holding the project's name and a link carrying `ssid=`), the "Saved successfully" confirmation and reopening a project at the designer URL come from the community desktop tool and could not be confirmed without the user's account; the manual checkpoint in the umbrella covers them.
- A held browser blocks the next fill (`busy`) until the user closes it or the server shuts down; shutting the server down closes the browser, and the saved project remains in the account.
- Google sign-in inside an automated browser may be refused by Google; the printer's own email sign-in is unaffected.
- CI installs no Playwright browser, so the fixture-site scenarios run only on machines with it.
