# Catalog face inventory: every Commander-legal layout carries its faces

Accepted for `mcp-catalog-face-inventory` under the [engine charter](../ENGINE-CHARTER.md). It closes the MCP ingestion gap the [legal-pool census](engine-any-corpus-inventory.md) routed here (`think:346`): 305 legal class, saga, case, leveler, mutate and prototype records carried `faces: null`, and those plus the 19 flip and 46 prepare records carried `face_relationship: "unsupported"`. The research finding and design are `think:410`; the implementation finding is `think:411`. Native Magistr records hold execution status.

The [source pin](../../engine/source.json) advances to canonical `mtg-game-engine` commit `52a93fa512672fd781bb5de8eb79ab64ed491588` on `main`. The root `Cargo.lock` is byte-identical. The authored worker contract gains eight `FaceRelationship` values; protocol 5 is kept, as it was when the seat count was widened, because the change only widens accepted input and the exact schema digest already rejects mixed artifacts. The catalog, preview and protocol fixtures are byte-identical.

## What the served data says

In the served snapshot (Scryfall oracle export of 2026-09-18, 31,830 Commander-legal identities), every adventure, flip, modal_dfc, prepare, split and transform record carries exactly two `card_faces`; every case, class, leveler, mutate, prototype and saga record carries none, like normal and meld. So the gap was two mapper rules, not missing source data: the root face was synthesized only for normal and meld, and the relationship label knew six layouts.

## Ownership and reuse review

- **One owner for the inventory.** The mapper stays the only place a face is synthesized; the census, the catalog capture and the Rust support inventory read the stored record. No consumer gained a second rule for "which faces exist".
- **One owner for the wire vocabulary.** The relationship enum is authored once in the engine repository's contract and generated into both languages; MCP's hand-written `CardGameplay` union mirrors it and the catalog capture validates through the generated schema.
- **Labels stay a layout classification.** Mapping the six single-faced special layouts to `single` was considered and rejected: the frozen TypeScript analysis paths treat `single` as a plain card, while prototype and mutate carry alternative costs and levelers and classes change characteristics; they must remain outside those paths until the Rust owners execute them. Per-layout labels also give `engine-any-layouts-special-actions` an explicit classification without a second field.
- **The index format announces the change.** Without the version bump an upgraded install would silently serve records that contradict the type documentation and the committed census until its next daily refresh; the project's index-version contract exists to prevent exactly that divergence.
- **Left with their recorded owners.** Runtime `Card` objects still carry no faces (`engine-any-layouts-special-actions`); the frozen TypeScript mana and construction paths still gate on `single` and are unchanged for these records; no construction rule changed.
- **Overlap.** None added. No TypeScript gameplay, no engine support-module change.

## Rules basis

From the retained Comprehensive Rules (20260819): 709 (split cards), 710 (flip cards), 711 (leveler cards), 712 (double-faced cards), 714 (Saga cards), 715 (Adventurer cards), 716 (Class cards), 719 (Case cards), 722 (preparation cards, whose inset prepare spell is the second supplied face), 701.42 (meld), 702.140 (mutate) and 702.160 (prototype). The label classifies the source; it never asserts which faces are playable.

## Limits

- The label is a classification of the source layout; face playability, flipping, level-up, chapter, class-level, prototype and mutate semantics belong to their engine owners.
- Every upgraded install must rebuild its index once (`data_ingest`); the rebuild downloads the bulk export again.
- The frozen TypeScript analysis paths still treat these 370 records as unknown for mana and construction purposes; that is deliberate until the Rust owners execute them.
