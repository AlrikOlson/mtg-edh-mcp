# Runtime support enforcement: unsupported semantics stop the run and say what they are

Accepted for `engine-mvp-support-runtime` under the [engine charter](../ENGINE-CHARTER.md). It is the runtime half that `think:302` split from [source-bound support qualification](engine-coverage.md), delivered after [bounded fixture execution](engine-preview-worker.md), [exact core state](engine-state.md) and [catalog objects](engine-mvp-catalog-objects.md). The research finding and plan are `think:413`; the implementation findings are `think:414`. Native Magistr records hold execution status.

The [source pin](../../engine/source.json) advances to canonical `mtg-game-engine` commit `618f006ac96b1f42386fbe9ccf25fc7ae2528a8c` on `main`. The root `Cargo.lock` and every generated contract derivative except the synced README are byte-identical; the worker contract schema is unchanged.

## Scope

Admission already refused every unsupported card before allocating anything, on both profiles: the fixture binding recomputes each report and rechecks the implementation digest, a run re-qualifies each card through `qualified_definition` on every trial, and the Commander owner qualifies every distinct identity and answers one `card_unsupported` per refusal. The wire carries no report field, so a report was never an admission credential. What was missing was the runtime half of the guard. Every canonical failure reached the worker as `GameOverReason::ExecutionError` and left as `engine_error/execution_error`: an unrepresented spell or ability effect, a trigger the scheduler could not announce, a choice shape or cost the owners cannot represent, and an engine request the fixture clients cannot answer were all reported as internal failures, with no object, card or behavior named. The core never counted them as a loss or resolved them silently (the execution-control unit made resolution transactional and removed the implicit passes); the gap was identification and honest classification.

## Ownership and reuse review

- **One executor, one classifier.** The core decides what it cannot execute and names the object; the worker translates that decision to the contract's existing `Diagnostic` (`oracle_id`, `physical_id`, `behavior_id` were already there), reading identities from the setup owner's inventory rather than keeping its own. No contract change, no second executor, no TypeScript gameplay.
- **Attribution lives where the object is known.** `UnsupportedEffect` learns its object at the four sites that already hold it; the loop supplies the acting card for a refused decision and the resolving object for a refused resolution. The worker never guesses: an injected object outside the inventory gets no physical or Oracle identity, and a token is named as a generated object.
- **A rejection is not a rules gap.** An illegal or stale decision, an inconsistent scheduler state and a policy failure remain `engine_error/execution_error`; only what the executor cannot represent is `unsupported`. An engine request none of this worker's clients can answer is `unsupported` because relaying decisions is a capability this worker declares it lacks (`decisions: false`).
- **The permissive builders are unreachable from a run, and a test says so.** The worker's sources reference none of `build_card_from_definition`, `CardBuilder`, `new_seeded`, `CardId::new`, `classify_card`, `oracle_parser`, `GameState::new`, `add_card_owned` or `create_token`; the session reaches the driver only through `execute`, and the driver only through `prepare_preview_game`. The factory remains available to the CLI and desktop as before, reached in the worker solely through `setup::build_game` after `qualified_definition`.
- **Both profiles share the guard.** The driver, the classifier and the attribution are profile-independent; a Commander trial, once the starting procedure exists, runs through the same seam and reports the same diagnostics with the scenario's `physical_id` labels. Profile-scoped fixture evidence still authorizes nothing under the Commander profile (`qualified_definition` refuses it).
- **Overlap.** None added.

## Rules basis

The Comprehensive Rules have no instruction for an effect the engine cannot carry out; the run is not a game, so no player loses (CR 104.1 and 104.2 name the only ways a game ends; 104.3 the only ways a player loses). The transactional stop preserves 733.1 (an illegal action is reversed, the game returns to the moment before it) and 117.4 (nothing resolves until every player passes), which is why a refused resolution leaves the object on the stack and a refused cast leaves the card in hand. Read from the engine's retained snapshot (`crates/mtg-engine/src/cards/support/preview_sources/comprehensive-rules.txt`).

## Limits

- No wire input can inject unsupported semantics into the immutable fixture, and no real deck is admitted yet, so the unsupported classification is proven in-process through the driver seam; the native suites prove honest classification of the outcomes a real run can reach today (completed, truncated, cancelled, refused).
- Semantics the engine does not know it lacks cannot stop a run: a permanent whose unmodeled ability is never enumerated plays as if it had none. That is exactly why admission qualifies every clause before allocation; the runtime guard catches what the executor meets, not what it never sees.
- The acting-card attribution is proven for a refused cast; a refused activation or mana activation with an unsupported cost choice is covered by the classifier scenario, not by a loop-level scenario, because no fixture card carries such a cost.
- One diagnostic per run: the first unsupported semantics stops the run, as the transactional executor cannot continue past it.
- A `ChoiceError::Unsupported` raised during a resolution with an empty stack would be attributed to no object; no current owner produces that combination.
